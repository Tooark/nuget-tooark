# Release Notes v5.0.0

Data de lançamento: janeiro de 2027 (previsão; rascunho em evolução na branch `release/v5`)

## 🆕 Resumo

Versão major. Reúne as quebras de compatibilidade anunciadas na [v4.8.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.8.0.md) e nas versões 4.x seguintes, todas com caminho de migração direto:

- **Só .NET 10.** Os pacotes deixam de ter o `net8.0` como alvo.
- **Membros obsoletos removidos:** `Notification.Clear()`, `GenerateString.Token()`, `RoleClaimsExtension.GetClaims()` sem parâmetros e `CryptographyOptions.Secret`.
- **Padrões e validações mais estritos:** as claims do JWT passam a sair com os nomes padrão, um `Cryptography:Algorithm` desconhecido falha no startup, a trava do armazenamento de chaves do Data Protection vem ligada em contêiner e a configuração estrita vem ligada por padrão.

Tudo o que a linha 4.x adicionou continua igual. Nenhum dado gravado pela 4.x fica ilegível: os valores cifrados com o `Secret` em texto abrem com o `SecretBase64` equivalente, e o modo `CBCUnsafe` continua disponível para descriptografar valores legados.

> Este arquivo é atualizado a cada quebra incorporada na branch. Antes de publicar: restaurar a baseline da validação de pacote na última 4.x publicada e gerar o `CompatibilitySuppressions.xml` só com as quebras listadas aqui.

## ⚠️ Mudanças Incompatíveis (todos os pacotes)

- **Alvo `net8.0` removido.** Os pacotes têm como alvo só o `net10.0`. O .NET 8 saiu do suporte da Microsoft em novembro de 2026 e deixou de receber correções de segurança. Uma aplicação ainda no .NET 8 não instala a v5: migre a aplicação para o .NET 10 antes, ou fique na linha 4.x, que mantém os dois alvos.
- Nenhuma API do Tooark muda por causa da troca de alvo.

## ⚠️ Mudanças Incompatíveis (Tooark.Notifications)

- **`Notification.Clear()` removido.** Era `protected`, estava marcado como obsoleto desde a v4.8.0 e colidia com métodos de domínio das entidades: um `Clear()` próprio ocultava o da base (`CS0108`). Use `ClearNotifications()`, disponível desde a v4.8.0 com o mesmo comportamento.
- Uma entidade ou value object que declare o próprio `Clear()` deixa de precisar do modificador `new`.

```csharp
// 4.x
protected void Reset() => Clear();

// v5
protected void Reset() => ClearNotifications();
```

## ⚠️ Mudanças Incompatíveis (Tooark.Utils)

- **`GenerateString.Token()` removido.** Estava obsoleto desde a v4.8.0: gerava só o texto, sem hash nem verificação. Use o `SecureToken.Create()` do `Tooark.Securities`, que acompanha `Hash` (o valor a guardar no banco) e `Verify` em tempo constante.
- O formato do token muda: Base64Url de 43 caracteres (32 bytes aleatórios) no lugar de 256 caracteres hexadecimais. Ajuste o tamanho da coluna e qualquer validação de formato. Tokens já emitidos não são afetados: a troca vale para os tokens novos.

```csharp
// 4.x
var token = GenerateString.Token();

// v5
var token = SecureToken.Create();      // vai para o usuário
var hash = SecureToken.Hash(token);    // vai para o banco
```

## ⚠️ Mudanças Incompatíveis (Tooark.Securities)

### Claims do JWT

- **Padrões das claims do JWT invertidos.** `JwtOptions.EmitStandardClaims` passa a `true` e `EmitLegacyClaims` a `false`. Um token emitido pelo `JwtTokenService` sem os sinalizadores explícitos passa a carregar `sub` e `preferred_username`, e não `id` e `login`. A claim `security` não muda.
- **`RoleClaimsExtension.GetClaims(JwtTokenDto)` removido.** A sobrecarga sem parâmetros estava obsoleta desde a v4.8.0: fixava os nomes legados e ignorava os sinalizadores das opções. Use `GetClaims(options)`, que segue a seção `Jwt`, ou `GetClaims(emitLegacyClaims, emitStandardClaims)`.
- O que **não** muda: o `UserTokenDto` continua lendo `id` e, na falta dele, `sub` (`login` e `preferred_username`), então tokens emitidos por um serviço 4.x seguem válidos; o `AddTooarkJwtBearer` valida os dois formatos; com os dois sinalizadores ligados o token carrega os dois conjuntos, que é o caminho de migração.

```json
// Quem ainda tem leitores de "id"/"login" mantém o conjunto legado ligado durante a migração
"Jwt": { "EmitLegacyClaims": true, "EmitStandardClaims": true }
```

```csharp
// 4.x
var claims = jwtToken.GetClaims();

// v5: os nomes saem das opções
var claims = jwtToken.GetClaims(jwtOptions.Value);

// Leitores: prefira as constantes, que já apontam para os nomes padrão
user.FindFirst(TooarkClaimNames.Subject)?.Value;            // "sub"
user.FindFirst(TooarkClaimNames.PreferredUsername)?.Value;  // "preferred_username"
```

### Criptografia

- **`CryptographyOptions.Secret` removido.** O `Secret` em texto estava obsoleto desde a v4.8.0: derivava a chave por um SHA-256 simples do texto, mais fraca do que uma chave aleatória. A chave passa a vir só de `SecretBase64` (ou de `Keys`). O `JwtOptions.Secret` não muda.
- **Não é preciso recifrar nada.** A chave que o `Secret` derivava é o SHA-256 do texto. Informe esse valor em `SecretBase64` e os valores cifrados na 4.x continuam abrindo, em `GCM`, `CBC` e `CBCUnsafe`:

```csharp
// Rode uma vez, com o texto que estava em Cryptography:Secret, e guarde o resultado em Cryptography:SecretBase64
var secretBase64 = Convert.ToBase64String(SHA256.HashData(Encoding.UTF8.GetBytes(secret)));
```

```json
// 4.x
"Cryptography": { "Algorithm": "GCM", "Secret": "minha-chave-secreta-32-caracteres" }

// v5
"Cryptography": { "Algorithm": "GCM", "SecretBase64": "<resultado do comando acima>" }
```

- **Sintoma de um `Secret` esquecido na configuração:** ele é ignorado. Sem `SecretBase64` nem `Keys`, o serviço falha com `Options.Cryptography.SecretNotConfigured` na primeira resolução do `ICryptographyService`. Quando a configuração estrita entrar (ainda pendente, veja abaixo), o startup passará a falhar antes, apontando a chave desconhecida.
- **`Cryptography:Algorithm` desconhecido falha no startup.** Um valor que não seja `GCM`, `CBC` ou `CBCUnsafe` (sem diferenciar maiúsculas) lança `Options.Cryptography.AlgorithmNotSupported;{valor}` no `AddTooarkCryptography`. Na 4.x um erro de digitação como `GMC` caía em `GCM` em silêncio. Ausente ou vazio continua valendo `GCM`.
- O que **não** muda: o modo `CBCUnsafe` continua disponível, somente para descriptografar valores legados cifrados com IV zero; o formato dos valores cifrados é o mesmo; o `IKeyedCryptographyService` e a rotação de chaves seguem iguais, com o `SecretBase64` no papel de chave legada.
- **Mensagens** (`Tooark.Extensions`, en-US/pt-BR/es-ES): chave nova `Options.Cryptography.AlgorithmNotSupported`; o texto de `Cryptography.LegacyKeyNotConfigured` deixa de citar o `Secret`.

### Data Protection

- **Trava do armazenamento de chaves ligada por padrão em contêiner.** Sem valor em `DataProtection:RequirePersistentKeyStorage`, a trava passa a valer quando a aplicação roda em contêiner. Na 4.x ela vinha desligada em qualquer ambiente, e o README do pacote já avisava a troca. Com a trava ligada e sem armazenamento de chaves (`KeysPath`, os callbacks `ReadKeys`/`WriteKey` ou um `PersistKeysTo*`), a aplicação não sobe: `Options.DataProtection.KeyStorageNotConfigured` no startup do host, ou no primeiro uso do Data Protection sem host.
- **Detecção de contêiner:** `DOTNET_RUNNING_IN_CONTAINER` com `true` ou `1`, que as imagens oficiais do .NET definem, ou `KUBERNETES_SERVICE_HOST` com qualquer valor, que o Kubernetes injeta em todo pod. Uma imagem própria fora do Kubernetes, sem nenhum dos dois, não é detectada.
- **O valor informado vence o padrão.** `true` liga a trava em qualquer ambiente; `false` a mantém desligada em contêiner, para uma API que não usa cookies nem protege dados com o Data Protection. Entre várias chamadas a `AddTooarkDataProtection`, vale a última que informou um valor.
- O que **não** muda: fora de contêiner o padrão continua desligado; quem não registra o Data Protection pelo Tooark (`AddTooarkDataProtection`, ou `AddTooarkSecurities` com a seção `DataProtection`, inclusive pelo `AddTooarkService` do agregador) não é afetado; a trava confere que o armazenamento existe, não que ele sobrevive à instância.
- **Limitação no Azure App Service:** o fallback nativo do ASP.NET Core, que grava as chaves em `%HOME%/ASP.NET/DataProtection-Keys`, não conta como armazenamento para a trava. Em um contêiner no App Service, aponte o `KeysPath` para a pasta persistente ou informe `false`.
- A mensagem de `Options.DataProtection.KeyStorageNotConfigured` passa a citar o `RequirePersistentKeyStorage` como saída para quem não depende de chaves persistentes.

```json
// Aplicação em contêiner que depende do Data Protection (cookies, OpenID Connect, tokens protegidos)
"DataProtection": { "ApplicationName": "minha-api", "KeysPath": "/var/dataprotection/keys" }

// Aplicação em contêiner que não depende de chaves persistentes
"DataProtection": { "ApplicationName": "minha-api", "RequirePersistentKeyStorage": false }
```

## ⚠️ Mudanças Incompatíveis (configuração estrita)

- **Pendente da v4.9.0.** A opção `Tooark:StrictConfiguration`, opt-in na v4.9.0, passa a ligada por padrão: uma seção do Tooark com chave desconhecida (`"SampligRatio"` em vez de `"SamplingRatio"`) falha o startup com `InvalidOperationException` apontando a chave. Chaves ausentes continuam opcionais, e pacotes não instalados não leem seção nenhuma. Para desligar, `"Tooark": { "StrictConfiguration": false }`.
- Limitação conhecida, a documentar com a implementação: os provedores de `Tooark.Secrets` e de `Tooark.Storage` compartilham a mesma seção com chaves diferentes; dois provedores da mesma família instalados juntos precisam desligar a opção.

## 🧭 Guia de migração da 4.x

1. Migre a aplicação para o **.NET 10**. A v5 não instala em .NET 8.
2. Atualize primeiro para a **última 4.x** e resolva os avisos de obsoleto:
   - `Clear()` → `ClearNotifications()`;
   - `GenerateString.Token()` → `SecureToken.Create()` (com `SecureToken.Hash` no banco);
   - `GetClaims()` → `GetClaims(options)`;
   - atribuição de `CryptographyOptions.Secret` em código → `SecretBase64`.
3. Na seção `Cryptography`, troque `Secret` por `SecretBase64` com o SHA-256 do texto em Base64 (comando acima). O aviso de obsoleto não aparece para quem define o `Secret` só no `appsettings.json`: confira a configuração de cada ambiente, inclusive os cofres de segredos. Confira também se `Algorithm` é `GCM`, `CBC` ou `CBCUnsafe`.
4. Na seção `Jwt`, defina `EmitLegacyClaims` e `EmitStandardClaims` de forma explícita. Com leitores antigos, ligue os dois; mova os leitores para `sub`/`preferred_username` (ou para o `UserTokenDto`) e desligue o legado depois.
5. Em contêiner, confira o Data Protection: se a aplicação chama `AddTooarkDataProtection` (ou `AddTooarkSecurities` com a seção `DataProtection`), configure um armazenamento de chaves compartilhado entre as instâncias, ou informe `"RequirePersistentKeyStorage": false` quando ela não depende de chaves persistentes. O valor já pode ser informado na 4.x.
6. Com a configuração estrita ligada por padrão, rode a aplicação em homologação: uma chave desconhecida em qualquer seção do Tooark falha o startup e aponta o nome errado.
7. Suba para a v5.

## Modificado

- **`AddTooarkCryptography`** devolve a exceção original do algoritmo desconhecido no registro, e não a `TargetInvocationException` em que o binder de configuração a embrulha.
- **Documentação**: READMEs do `Tooark.Notifications`, do `Tooark.Securities` e do `Tooark.Utils` (en/pt-BR) refletem os membros removidos, os novos padrões das claims, o algoritmo estrito e o padrão da trava do Data Protection em contêiner, com a nota de migração da 4.x. O README da raiz, o `CONTRIBUTING.md`, o `SECURITY.md` e o README dos testes descrevem o alvo único.

## Suporte das versões

- **5.x** é a linha ativa: funcionalidades novas, correções e correções de segurança.
- **4.x** passa a receber só atualizações de dependências para corrigir vulnerabilidades. Funcionalidades novas entram na 5.x. O `SECURITY.md` traz a tabela atualizada.

## Infraestrutura do repositório

- **Alvo único**: todos os projetos passam de `net8.0;net10.0` para `net10.0`. Os pins atrelados ao runtime ficam em um grupo só no `Directory.Packages.props`, na linha 10.0.x; saem o grupo 8.0.x, o `scripts/check-package-pairs.sh` e o passo do CI que conferia os pares. Os workflows instalam só o SDK 10.
- **Dependabot**: volta a propor os patches dos pacotes atrelados ao runtime, que na 4.x eram atualizados à mão, em pares. Só a troca de major fica ignorada, porque acompanha a troca do alvo.
- **Validação da API pública**: a baseline do `EnablePackageValidation` fica desligada durante o desenvolvimento da major, porque as quebras acima são intencionais. Antes da publicação, a baseline volta para a última 4.x publicada e o `CompatibilitySuppressions.xml` registra só as quebras deste arquivo (`dotnet pack /p:GenerateCompatibilitySuppressionFile=true`).

## Impacto

- Quem já está no .NET 10, resolveu os avisos de obsoleto na 4.x, trocou o `Secret` por `SecretBase64` na configuração e definiu os dois sinalizadores de claims não precisa mudar código ao atualizar.
- Quem ainda está no .NET 8 não consegue instalar a v5 e continua na linha 4.x.
- Quem depende do padrão das claims recebe tokens com `sub`/`preferred_username`: clientes que leem `id`/`login` direto do token param de encontrar as claims até ligar `EmitLegacyClaims` ou migrar a leitura.
- Quem deixar o `Secret` em texto na configuração vê o serviço de criptografia falhar por falta de chave. Nenhum valor cifrado é perdido: basta informar o `SecretBase64` equivalente.
- Quem tinha um `Algorithm` digitado errado estava cifrando em `GCM` sem saber, e passa a ver a falha no startup. Corrija o valor para `GCM` e os dados continuam abrindo.
- Quem registra o Data Protection pelo Tooark em contêiner, sem armazenamento de chaves e sem informar `RequirePersistentKeyStorage`, vê a aplicação deixar de subir. É o comportamento pretendido: antes a aplicação subia e perdia as chaves quando o contêiner era recriado.
- Compatível com .NET 10.0+.

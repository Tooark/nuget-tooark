# Release Notes v5.0.0

Data de lançamento: dezembro de 2026

## 🆕 Resumo

Versão major. Reúne as quebras de compatibilidade anunciadas na [v4.8.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.8.0.md) e nas versões 4.x seguintes, todas com caminho de migração direto:

- **Só .NET 10.** Os pacotes deixam de ter o `net8.0` como alvo.
- **Membros obsoletos removidos:** `Notification.Clear()`, `GenerateString.Token()`, `RoleClaimsExtension.GetClaims()` sem parâmetros e `CryptographyOptions.Secret`.
- **Padrões e validações mais estritos:** as claims do JWT passam a sair com os nomes padrão, um `Cryptography:Algorithm` desconhecido falha no startup, a trava do armazenamento de chaves do Data Protection vem ligada em contêiner, a configuração estrita vem ligada por padrão, e a guarda de saída do `Tooark.Http` confere o nome do destino também atrás de um proxy.
- **Problem Details:** um 4xx do `TooarkExceptionHandler` passa a ser registrado em `Information`, e as falhas de validação do ASP.NET Core passam a sair na mesma lista `errors` das exceções. As duas opções surgiram desligadas na v4.10.0 e passam a vir ligadas.

Tudo o que a linha 4.x adicionou continua igual, inclusive o que entrou na [v4.10.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.10.0.md): os construtores com identificador das entidades, o `SetId` que lança, as `TooarkProblemDetailsOptions` e o `ValidationProblemExtension`. Quem pula a v4.10.0 recebe junto a mudança do `SetId`, e o Impacto das notas dela mostra a migração. Nenhum dado gravado pela 4.x fica ilegível: os valores cifrados com o `Secret` em texto abrem com o `SecretBase64` equivalente, e o modo `CBCUnsafe` continua disponível para descriptografar valores legados.

## ⚠️ Mudanças Incompatíveis (todos os pacotes)

- **Alvo `net8.0` removido.** Os pacotes têm como alvo só o `net10.0`. O .NET 8 saiu do suporte da Microsoft em novembro de 2026 e deixou de receber correções de segurança. Uma aplicação ainda no .NET 8 não instala a v5: migre a aplicação para o .NET 10 antes, ou fique na linha 4.x, que mantém os dois alvos.
- Nenhuma API do Tooark muda por causa da troca de alvo.

## ⚠️ Mudanças Incompatíveis (Tooark.Notifications)

- **`Notification.Clear()` removido.** Era `protected`, estava marcado como obsoleto desde a v4.8.0 e colidia com métodos de domínio das entidades: um `Clear()` próprio ocultava o da base (`CS0108`). Use `ClearNotifications()`, disponível desde a v4.8.0 com o mesmo comportamento.
- Uma entidade ou value object que declare o próprio `Clear()` deixa de precisar do modificador `new`.

```csharp
// 4.x
protected void Reset() => Clear();

// v5
protected void Reset() => ClearNotifications();
```

## ⚠️ Mudanças Incompatíveis (Tooark.Utils)

- **`GenerateString.Token()` removido.** Estava obsoleto desde a v4.8.0: gerava só o texto, sem hash nem verificação. Use o `SecureToken.Create()` do `Tooark.Securities`, que acompanha `Hash` (o valor a guardar no banco) e `Verify` em tempo constante.
- O formato do token muda: Base64Url de 43 caracteres (32 bytes aleatórios) no lugar de 256 caracteres hexadecimais. Ajuste o tamanho da coluna e qualquer validação de formato. Tokens já emitidos não são afetados: a troca vale para os tokens novos.

```csharp
// 4.x
var token = GenerateString.Token();

// v5
var token = SecureToken.Create();      // vai para o usuário
var hash = SecureToken.Hash(token);    // vai para o banco
```

## ⚠️ Mudanças Incompatíveis (Tooark.Securities)

### Claims do JWT

- **Padrões das claims do JWT invertidos.** `JwtOptions.EmitStandardClaims` passa a `true` e `EmitLegacyClaims` a `false`. Um token emitido pelo `JwtTokenService` sem os sinalizadores explícitos passa a carregar `sub` e `preferred_username`, e não `id` e `login`. A claim `security` não muda.
- **`RoleClaimsExtension.GetClaims(JwtTokenDto)` removido.** A sobrecarga sem parâmetros estava obsoleta desde a v4.8.0: fixava os nomes legados e ignorava os sinalizadores das opções. Use `GetClaims(options)`, que segue a seção `Jwt`, ou `GetClaims(emitLegacyClaims, emitStandardClaims)`.
- O que **não** muda: o `UserTokenDto` continua lendo `id` e, na falta dele, `sub` (`login` e `preferred_username`), então tokens emitidos por um serviço 4.x seguem válidos; o `AddTooarkJwtBearer` valida os dois formatos; com os dois sinalizadores ligados o token carrega os dois conjuntos, que é o caminho de migração.

```json
// Quem ainda tem leitores de "id"/"login" mantém o conjunto legado ligado durante a migração
"Jwt": { "EmitLegacyClaims": true, "EmitStandardClaims": true }
```

```csharp
// 4.x
var claims = jwtToken.GetClaims();

// v5: os nomes saem das opções
var claims = jwtToken.GetClaims(jwtOptions.Value);

// Leitores: prefira as constantes, que já apontam para os nomes padrão
user.FindFirst(TooarkClaimNames.Subject)?.Value;            // "sub"
user.FindFirst(TooarkClaimNames.PreferredUsername)?.Value;  // "preferred_username"
```

### Criptografia

- **`CryptographyOptions.Secret` removido.** O `Secret` em texto estava obsoleto desde a v4.8.0: derivava a chave por um SHA-256 simples do texto, mais fraca do que uma chave aleatória. A chave passa a vir só de `SecretBase64` (ou de `Keys`). O `JwtOptions.Secret` não muda.
- **Não é preciso recifrar nada.** A chave que o `Secret` derivava é o SHA-256 do texto. Informe esse valor em `SecretBase64` e os valores cifrados na 4.x continuam abrindo, em `GCM`, `CBC` e `CBCUnsafe`:

```csharp
// Rode uma vez, com o texto que estava em Cryptography:Secret, e guarde o resultado em Cryptography:SecretBase64
var secretBase64 = Convert.ToBase64String(SHA256.HashData(Encoding.UTF8.GetBytes(secret)));
```

```json
// 4.x
"Cryptography": { "Algorithm": "GCM", "Secret": "minha-chave-secreta-32-caracteres" }

// v5
"Cryptography": { "Algorithm": "GCM", "SecretBase64": "<resultado do comando acima>" }
```

- **Sintoma de um `Secret` esquecido na configuração:** a aplicação não sobe. Com a configuração estrita, ligada por padrão (veja abaixo), o `AddTooarkCryptography` falha com `Options.Configuration.UnknownKey;Cryptography;Secret`, que aponta a chave que sobrou. Com a configuração estrita desligada o `Secret` é ignorado e, sem `SecretBase64` nem `Keys`, o serviço falha com `Options.Cryptography.SecretNotConfigured` na primeira resolução do `ICryptographyService`.
- **`Cryptography:Algorithm` desconhecido falha no startup.** Um valor que não seja `GCM`, `CBC` ou `CBCUnsafe` (sem diferenciar maiúsculas) lança `Options.Cryptography.AlgorithmNotSupported;{valor}` no `AddTooarkCryptography`. Na 4.x um erro de digitação como `GMC` caía em `GCM` em silêncio. Ausente ou vazio continua valendo `GCM`.
- O que **não** muda: o modo `CBCUnsafe` continua disponível, somente para descriptografar valores legados cifrados com IV zero; o formato dos valores cifrados é o mesmo; o `IKeyedCryptographyService` e a rotação de chaves seguem iguais, com o `SecretBase64` no papel de chave legada.
- **Mensagens** (`Tooark.Extensions`, en-US/pt-BR/es-ES): chave nova `Options.Cryptography.AlgorithmNotSupported`; o texto de `Cryptography.LegacyKeyNotConfigured` deixa de citar o `Secret`.

### Data Protection

- **Trava do armazenamento de chaves ligada por padrão em contêiner.** Sem valor em `DataProtection:RequirePersistentKeyStorage`, a trava passa a valer quando a aplicação roda em contêiner. Na 4.x ela vinha desligada em qualquer ambiente, e o README do pacote já avisava a troca. Com a trava ligada e sem armazenamento de chaves (`KeysPath`, os callbacks `ReadKeys`/`WriteKey` ou um `PersistKeysTo*`), a aplicação não sobe: `Options.DataProtection.KeyStorageNotConfigured` no startup do host, ou no primeiro uso do Data Protection sem host.
- **Detecção de contêiner:** `DOTNET_RUNNING_IN_CONTAINER` com `true` ou `1`, que as imagens oficiais do .NET definem, ou `KUBERNETES_SERVICE_HOST` com qualquer valor, que o Kubernetes injeta em todo pod. Uma imagem própria fora do Kubernetes, sem nenhum dos dois, não é detectada.
- **O valor informado vence o padrão.** `true` liga a trava em qualquer ambiente; `false` a mantém desligada em contêiner, para uma API que não usa cookies nem protege dados com o Data Protection. Entre várias chamadas a `AddTooarkDataProtection`, vale a última que informou um valor.
- O que **não** muda: fora de contêiner o padrão continua desligado; quem não registra o Data Protection pelo Tooark (`AddTooarkDataProtection`, ou `AddTooarkSecurities` com a seção `DataProtection`, inclusive pelo `AddTooarkService` do agregador) não é afetado; a trava confere que o armazenamento existe, não que ele sobrevive à instância.
- **Limitação no Azure App Service:** o fallback nativo do ASP.NET Core, que grava as chaves em `%HOME%/ASP.NET/DataProtection-Keys`, não conta como armazenamento para a trava. Em um contêiner no App Service, aponte o `KeysPath` para a pasta persistente ou informe `false`.
- A mensagem de `Options.DataProtection.KeyStorageNotConfigured` passa a citar o `RequirePersistentKeyStorage` como saída para quem não depende de chaves persistentes.

```json
// Aplicação em contêiner que depende do Data Protection (cookies, OpenID Connect, tokens protegidos)
"DataProtection": { "ApplicationName": "minha-api", "KeysPath": "/var/dataprotection/keys" }

// Aplicação em contêiner que não depende de chaves persistentes
"DataProtection": { "ApplicationName": "minha-api", "RequirePersistentKeyStorage": false }
```

## ⚠️ Mudanças Incompatíveis (configuração estrita)

- **`Tooark:StrictConfiguration` passa a valer `true` quando não informada.** A opção era opt-in na v4.9.0. Uma seção lida por um pacote Tooark com uma chave que ele não conhece (`"SampligRatio"` em vez de `"SamplingRatio"`) impede a aplicação de subir, com `Options.Configuration.UnknownKey;{seção};{chaves}` (`InternalServerErrorException`) no registro (`AddTooark...`). Seções conferidas: `Cryptography`, `DataProtection`, `HttpClient`, `Jwt`, `Observability`, `OpenId:{provedor}`, `PasswordHash`, `Sanitizers`, `Secrets` e `Storage`.
- **O que entra na conta:** toda fonte de configuração. Uma variável de ambiente como `Jwt__Qualquer`, um segredo carregado de um cofre para dentro de uma seção e uma chave de versão antiga (o `Cryptography:Secret` removido nesta versão) também são chaves da seção.
- **O que não muda:** chaves ausentes continuam opcionais; um pacote que a aplicação não registra não confere nada; as outras seções da aplicação (`Logging`, as suas) não são tocadas.
- **Para desligar:** `"Tooark": { "StrictConfiguration": false }`, que devolve o comportamento da linha 4.x.
- **Limitação:** dois provedores da mesma família registrados juntos (`Tooark.Storage.Aws` e `Tooark.Storage.Gcp`, ou dois do `Tooark.Secrets`) leem a mesma seção com chaves diferentes, e um recusa as chaves do outro. Desligue a opção nesse caso.

```json
// v5: desliga a conferência das chaves desconhecidas
"Tooark": { "StrictConfiguration": false }
```

## ⚠️ Mudanças Incompatíveis (Tooark.Http)

- **Guarda de saída atrás de um proxy: o nome do destino passa a ser conferido.** Com um proxy de saída (`HTTP_PROXY`/`HTTPS_PROXY` ou `SocketsHttpHandler.Proxy`), a conexão é aberta para o proxy, e na v4.9.0 só o IP literal da URL era conferido. Agora a guarda resolve o nome pelo DNS da aplicação antes de enviar e recusa, com `Http.OutboundBlocked;{host}`, o que resolve para um endereço bloqueado. A requisição não chega ao proxy; em `https`, nem o `CONNECT` é enviado.
- **Nome que a aplicação não consegue resolver é recusado.** A guarda recusa o que não consegue conferir: a requisição falha como falha de conexão (`Http.ConnectionFailed`, repetida pela resiliência), sem chegar ao proxy. Em redes em que só o proxy tem DNS para nomes externos, informe `"OutboundGuard": { "AllowUnresolvedHostsBehindProxy": true }` (opção nova): os nomes que a aplicação não resolve passam sem conferência.
- **Handler primário trocado depois da guarda.** A mesma conferência antes do envio vale quando o handler primário do cliente não é o da guarda. Antes, nesse caso, só o IP literal era conferido.
- O que **não** muda: sem proxy, o nome continua conferido uma vez só, na conexão, sem consulta a mais ao DNS; os nomes em `AllowedHosts` não são consultados; uma URI que o proxy dispensa (`NO_PROXY`) vai direto e é conferida na conexão.
- **Continua sendo um filtro, e não uma garantia**, quando há um proxy: ele resolve o nome de novo, e os saltos de um redirecionamento só ele vê. Mantenha o bloqueio das faixas internas nas regras do proxy.

```json
// Rede em que só o proxy resolve nomes externos
"HttpClient": { "OutboundGuard": { "Enabled": true, "AllowUnresolvedHostsBehindProxy": true } }
```

## ⚠️ Mudanças Incompatíveis (Tooark.AspNetCore)

### Nível do log das exceções tratadas

- **Um 4xx passa a ser registrado em `Information`, e não em `Warning`.** Um 404 ou um 409 faz parte da operação normal e enchia o log de avisos. Um 5xx continua em `Error`, com a exceção e a pilha de chamadas.
- O nível já é configurável desde a v4.10.0, com as `TooarkProblemDetailsOptions`; o que muda é o padrão de `ClientErrorLogLevel`. No .NET 10 o `UseExceptionHandler` não registra a exceção que um `IExceptionHandler` tratou, então o registro do manipulador é o único da exceção.

```csharp
// Volta ao comportamento da 4.x para os 4xx e tira os não encontrados do log de produção
builder.Services.Configure<TooarkProblemDetailsOptions>(options =>
{
  options.ClientErrorLogLevel = LogLevel.Warning;
  options.StatusCodeLogLevels[StatusCodes.Status404NotFound] = LogLevel.Debug;
});
```

### Falhas de validação na lista do Tooark

- **`ConvertValidationProblems` passa a vir ligada.** Com o `AddTooarkProblemDetails`, as falhas de validação do ASP.NET Core saem na lista `errors` do Tooark, a mesma das exceções, e não mais no objeto por campo do `ValidationProblemDetails`. Cada mensagem vira um item, com o campo em `key`, o código padrão `T.ERR` e a mensagem traduzida; o `title` passa a ser a frase padrão do status (`Bad Request`). As extensões do `CustomizeProblemDetails` continuam no corpo; um `title` ou um `detail` definido nele é substituído.
- **Motivo:** com os dois formatos na mesma chave, o cliente não sabia, pela chave, qual deles recebeu. Agora `errors` é sempre a lista.
- **Onde vale:** a validação automática dos controllers com `[ApiController]` (sem o envelope do `AddTooarkModelStateEnvelope`, que continua respondendo o `ResponseDto`), o `ValidationProblem()` dos controllers, a validação das minimal APIs e o `Results.ValidationProblem`.
- **Quem lê o corpo:** clientes que leem `errors` como objeto por campo (`errors.Email[0]`) passam a receber a lista. A opção existe desde a v4.10.0: ligue-a em homologação para ajustar os clientes antes da troca de versão, ou desligue-a na v5 para manter o formato do ASP.NET Core.

```json
// 4.x (e v5 com ConvertValidationProblems = false)
{ "status": 400, "title": "One or more validation errors occurred.", "errors": { "Email": ["The Email field is required."] } }

// v5
{ "status": 400, "title": "Bad Request", "detail": "The Email field is required.", "errors": [{ "code": "T.ERR", "key": "Email", "message": "The Email field is required." }] }
```

## 🧭 Guia de migração da 4.x

1. Migre a aplicação para o **.NET 10**. A v5 não instala em .NET 8.
2. Atualize primeiro para a **última 4.x** e resolva os avisos de obsoleto:
   - `Clear()` → `ClearNotifications()`;
   - `GenerateString.Token()` → `SecureToken.Create()` (com `SecureToken.Hash` no banco);
   - `GetClaims()` → `GetClaims(options)`;
   - atribuição de `CryptographyOptions.Secret` em código → `SecretBase64`.
3. Na seção `Cryptography`, troque `Secret` por `SecretBase64` com o SHA-256 do texto em Base64 (comando acima). O aviso de obsoleto não aparece para quem define o `Secret` só no `appsettings.json`: confira a configuração de cada ambiente, inclusive os cofres de segredos. Confira também se `Algorithm` é `GCM`, `CBC` ou `CBCUnsafe`.
4. Na seção `Jwt`, defina `EmitLegacyClaims` e `EmitStandardClaims` de forma explícita. Com leitores antigos, ligue os dois; mova os leitores para `sub`/`preferred_username` (ou para o `UserTokenDto`) e desligue o legado depois.
5. Em contêiner, confira o Data Protection: se a aplicação chama `AddTooarkDataProtection` (ou `AddTooarkSecurities` com a seção `DataProtection`), configure um armazenamento de chaves compartilhado entre as instâncias, ou informe `"RequirePersistentKeyStorage": false` quando ela não depende de chaves persistentes. O valor já pode ser informado na 4.x.
6. A configuração estrita vem ligada por padrão. Para encontrar as chaves erradas antes da troca de versão, ligue `"Tooark": { "StrictConfiguration": true }` na última 4.x (a opção existe desde a v4.9.0) e rode a aplicação em homologação: uma chave desconhecida em qualquer seção do Tooark impede a aplicação de subir e aponta a seção e o nome errado.
7. Se a aplicação usa a guarda de saída do `Tooark.Http` atrás de um proxy, confira se ela resolve os nomes dos destinos. Se só o proxy os resolve, informe `AllowUnresolvedHostsBehindProxy`; um serviço interno alcançado pelo proxy entra em `AllowedHosts`.
8. Se a aplicação filtra o log por `Warning` para acompanhar os 4xx, ajuste o filtro ou informe `ClientErrorLogLevel = LogLevel.Warning` nas `TooarkProblemDetailsOptions`.
9. Se a API usa o `AddTooarkProblemDetails` e os clientes leem o `errors` das falhas de validação como objeto por campo, ligue `ConvertValidationProblems` na última 4.x e ajuste os clientes para a lista, ou informe `false` na v5 para manter o formato do ASP.NET Core.
10. Suba para a v5.

## Modificado

- **`AddTooarkCryptography`** devolve a exceção original do algoritmo desconhecido no registro, e não a `TargetInvocationException` em que o binder de configuração a embrulha.
- **`Tooark.Http` e `Tooark.Entities.EntityFrameworkCore`**, adicionados na v4.9.0, passam a ter só o `net10.0` como alvo, como os demais. O `ApplyTooarkConventions()` fica só com o caminho do Entity Framework Core 10, sem mudança de comportamento para quem já estava no .NET 10.
- **Dependências** (só os pacotes indicados recebem a versão nova):
  - `OpenTelemetry`, `OpenTelemetry.Exporter.Console`, `OpenTelemetry.Exporter.OpenTelemetryProtocol`, `OpenTelemetry.Extensions.Hosting` e `OpenTelemetry.Instrumentation.Runtime` 1.20.1 → 1.21.0, `OpenTelemetry.Instrumentation.AspNetCore` e `Http` 1.20.2 → 1.21.0 e `OpenTelemetry.Instrumentation.Process` 1.20.1-rc.1 → 1.21.0-rc.1 (`Tooark.Observability`). A linha 1.21 tirou o `net8.0`, por isso só entra na v5; no `net10.0` ela pede o `Microsoft.Extensions.*` 10.0, que os pins já cobrem. O que muda para quem consome:
    - os provedores passam a iniciar no `StartingAsync` do host, e a telemetria emitida por outros hosted services nessa fase passa a ser capturada;
    - a descrição do status do span (`otel.status_description`) passa a ser cortada no limite de tamanho dos atributos (`OTEL_SPAN_ATTRIBUTE_VALUE_LENGTH_LIMIT`);
    - o `OTEL_RESOURCE_ATTRIBUTES` deixa de trocar `+` por espaço;
    - os recursos passam às convenções semânticas 1.45.0, sem mudança nos nomes das métricas de processo;
    - o `OTEL_DIAGNOSTICS.json` passa a gravar arquivos `otel-dotnet-*.log` rotativos;
    - a retentativa em disco do exportador OTLP, que é experimental, passa a conferir as permissões do diretório fora do Windows.
  - `AWSSDK.S3` 4.0.104.11 → 4.1.0 (`Tooark.Storage.Aws`), `AWSSDK.SecretsManager` 4.0.100.25 → 4.1.1 e `AWSSDK.SimpleSystemsManagement` 4.0.105 → 4.1.1 (`Tooark.Secrets.Aws`). O `AWSSDK.Core` 4.1 traz duas dependências transitivas novas: `AWSSDK.Extensions.Numerics` e `System.IO.Hashing` 11.0. Como o `System.IO.Hashing` 11 não suporta o `net8.0`, a linha 4.1 também só entra na v5.
  - `HtmlSanitizer` 10.0.1120 → 11.0.26 (`Tooark.Sanitizers`), com o `AngleSharp` 1.9.0 → 1.10.0 e o `AngleSharp.Css` 1.3.1 → 1.4.0. A API do Tooark não muda, mas a sanitização fica mais estrita:
    - o `name` sai sempre de `embed`, `form`, `iframe`, `img` e `object`, mesmo liberado em `AllowedAttributes`, contra o DOM clobbering;
    - o `contenteditable` deixa a lista padrão de atributos e volta quando informado em `AllowedAttributes`.

    Vem da `main` ([PR #90](https://github.com/Tooark/nuget-tooark/pull/90)).
- **Documentação**: READMEs do `Tooark.AspNetCore` (en/pt-BR) com os padrões da v5 do log e da conversão das falhas de validação. READMEs do `Tooark.Notifications`, do `Tooark.Securities` e do `Tooark.Utils` (en/pt-BR) refletem os membros removidos, os novos padrões das claims, o algoritmo estrito e o padrão da trava do Data Protection em contêiner, com a nota de migração da 4.x. O README da raiz, o `CONTRIBUTING.md`, o `SECURITY.md` e o README dos testes descrevem o alvo único. O README do `Tooark.Sanitizers` (en/pt-BR) explica o tratamento do `name` e do `contenteditable` e cita o HtmlSanitizer 11.x.

## Suporte das versões

- **5.x** é a linha ativa: funcionalidades novas, correções e correções de segurança.
- **4.x** passa a receber só atualizações de dependências para corrigir vulnerabilidades. Funcionalidades novas entram na 5.x.
- **2.x e 3.x** continuam recebendo correções de segurança até o fim de dezembro de 2026, como anunciado, e ficam encerradas a partir de janeiro de 2027 (últimas versões até aqui: v2.3.6 e v3.3.7). O `SECURITY.md` traz a tabela atualizada.

## Infraestrutura do repositório

- **Alvo único**: todos os projetos passam de `net8.0;net10.0` para `net10.0`. Os pins atrelados ao runtime ficam em um grupo só no `Directory.Packages.props`, na linha 10.0.x; saem o grupo 8.0.x, o `scripts/check-package-pairs.sh` e o passo do CI que conferia os pares. Os workflows instalam só o SDK 10.
- **Dependabot**: volta a propor os patches dos pacotes atrelados ao runtime, que na 4.x eram atualizados à mão, em pares. Só a troca de major fica ignorada, porque acompanha a troca do alvo.
- **Testes**: `Microsoft.NET.Test.Sdk` 18.11.0 → 18.12.0, `coverlet.MTP` 10.1.0 → 10.1.1 e `ReportGenerator` 5.5.12 → 5.6.0. O `System.IO.Abstractions`, referenciado pelo projeto de testes sem uso, sai. Só o projeto de testes usa esses pacotes; vêm da `main` ([PR #90](https://github.com/Tooark/nuget-tooark/pull/90)).
- **Validação da API pública**: a baseline do `EnablePackageValidation` passa da v4.9.0 para a v4.10.0, a última 4.x. As quebras de API desta versão ficam registradas no `CompatibilitySuppressions.xml` de cada pacote: o alvo `net8.0`, nos 28 pacotes, e os membros removidos (`Notification.Clear()`, `GenerateString.Token(int)`, `RoleClaimsExtension.GetClaims(JwtTokenDto)` e o `get`/`set` de `CryptographyOptions.Secret`). Qualquer outra quebra falha o `dotnet pack`. As trocas de padrão (claims, configuração estrita, Data Protection, log, conversão das falhas de validação) não mudam a assinatura de nenhum membro e não aparecem nesses arquivos. O CI dos pull requests passa a rodar o `dotnet pack`, e uma quebra sem supressão falha o pull request, e não só a publicação.

## Impacto

- Quem já está no .NET 10, resolveu os avisos de obsoleto na 4.x, trocou o `Secret` por `SecretBase64` na configuração e definiu os dois sinalizadores de claims não precisa mudar código ao atualizar.
- Quem ainda está no .NET 8 não consegue instalar a v5 e continua na linha 4.x.
- Quem depende do padrão das claims recebe tokens com `sub`/`preferred_username`: clientes que leem `id`/`login` direto do token param de encontrar as claims até ligar `EmitLegacyClaims` ou migrar a leitura.
- Quem deixar o `Secret` em texto na configuração vê a aplicação deixar de subir, com a mensagem apontando a chave `Secret` (com a configuração estrita desligada, é o serviço de criptografia que falha, por falta de chave). Nenhum valor cifrado é perdido: basta informar o `SecretBase64` equivalente.
- Quem usa a guarda de saída atrás de um proxy passa a ter os nomes dos destinos conferidos antes do envio. Um destino que resolve para a rede interna deixa de chegar ao proxy, e um nome que a aplicação não resolve falha como falha de conexão até a opção `AllowUnresolvedHostsBehindProxy` ser informada.
- Quem tem uma chave desconhecida em alguma seção lida pelos pacotes Tooark (um erro de digitação, uma chave de versão antiga, uma variável de ambiente a mais) vê a aplicação deixar de subir, com a seção e a chave na mensagem. Corrija ou remova a chave, ou desligue a configuração estrita.
- Quem tinha um `Algorithm` digitado errado estava cifrando em `GCM` sem saber, e passa a ver a falha no startup. Corrija o valor para `GCM` e os dados continuam abrindo.
- Quem registra o Data Protection pelo Tooark em contêiner, sem armazenamento de chaves e sem informar `RequirePersistentKeyStorage`, vê a aplicação deixar de subir. É o comportamento pretendido: antes a aplicação subia e perdia as chaves quando o contêiner era recriado.
- Quem usa o `Tooark.Sanitizers` com `img`, `form` ou `iframe` liberados perde o atributo `name` nesses elementos, e o `contenteditable` só passa quando estiver em `AllowedAttributes`.
- Quem conta os `Warning` do `TooarkExceptionHandler` para acompanhar os 4xx passa a vê-los em `Information`.
- Quem lê o `errors` das falhas de validação do ASP.NET Core como objeto por campo passa a receber a lista do Tooark, até desligar `ConvertValidationProblems`.
- Compatível com .NET 10.0+.

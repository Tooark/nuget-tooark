# Release Notes v5.0.0

Data de lançamento: janeiro de 2027 (previsão; rascunho em evolução na branch `release/v5`)

## 🆕 Resumo

Versão major. Reúne as quebras de compatibilidade anunciadas na [v4.8.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.8.0.md) e nas versões 4.x seguintes, todas pequenas e com caminho de migração direto: a remoção do `Notification.Clear()`, a inversão dos padrões das claims do JWT e a configuração estrita ligada por padrão. Tudo o que a linha 4.x adicionou continua igual.

> Este arquivo é atualizado a cada quebra incorporada na branch. Antes de publicar: restaurar a baseline da validação de pacote na última 4.x publicada e gerar o `CompatibilitySuppressions.xml` só com as quebras listadas aqui.

---

## ⚠️ Mudanças Incompatíveis (Tooark.Notifications)

- **`Notification.Clear()` removido.** Era `protected`, estava marcado como obsoleto desde a v4.8.0 e colidia com métodos de domínio das entidades: um `Clear()` próprio ocultava o da base (`CS0108`). Use `ClearNotifications()`, disponível desde a v4.8.0 com o mesmo comportamento.
- Uma entidade ou value object que declare o próprio `Clear()` deixa de precisar do modificador `new`.

```csharp
// 4.x
protected void Reset() => Clear();

// v5
protected void Reset() => ClearNotifications();
```

## ⚠️ Mudanças Incompatíveis (Tooark.Securities)

- **Padrões das claims do JWT invertidos.** `JwtOptions.EmitStandardClaims` passa a `true` e `EmitLegacyClaims` a `false`. Um token emitido pelo `JwtTokenService` sem os sinalizadores explícitos passa a carregar `sub` e `preferred_username`, e não `id` e `login`. A claim `security` não muda.
- **`RoleClaimsExtension.GetClaims(JwtTokenDto)`** (sobrecarga sem parâmetros) passa a emitir os nomes padrão, acompanhando os padrões das opções. As sobrecargas com `JwtOptions` ou com os dois sinalizadores não mudam.
- O que **não** muda: o `UserTokenDto` continua lendo `id` e, na falta dele, `sub` (`login` e `preferred_username`), então tokens emitidos por um serviço 4.x seguem válidos; o `AddTooarkJwtBearer` valida os dois formatos; com os dois sinalizadores ligados o token carrega os dois conjuntos, que é o caminho de migração.

```json
// Quem ainda tem leitores de "id"/"login" mantém o conjunto legado ligado durante a migração
"Jwt": { "EmitLegacyClaims": true, "EmitStandardClaims": true }
```

```csharp
// Leitores: prefira as constantes, que já apontam para os nomes padrão
user.FindFirst(TooarkClaimNames.Subject)?.Value;            // "sub"
user.FindFirst(TooarkClaimNames.PreferredUsername)?.Value;  // "preferred_username"
```

## ⚠️ Mudanças Incompatíveis (configuração estrita)

- **Pendente da v4.9.0.** A opção `Tooark:StrictConfiguration`, opt-in na v4.9.0, passa a ligada por padrão: uma seção do Tooark com chave desconhecida (`"SampligRatio"` em vez de `"SamplingRatio"`) falha o startup com `InvalidOperationException` apontando a chave. Chaves ausentes continuam opcionais, e pacotes não instalados não leem seção nenhuma. Para desligar, `"Tooark": { "StrictConfiguration": false }`.
- Limitação conhecida, a documentar com a implementação: os provedores de `Tooark.Secrets` e de `Tooark.Storage` compartilham a mesma seção com chaves diferentes; dois provedores da mesma família instalados juntos precisam desligar a opção.

---

## 🧭 Guia de migração da 4.x

1. Atualize primeiro para a **última 4.x** e resolva os avisos de obsoleto: `Clear()` → `ClearNotifications()`.
2. Na seção `Jwt`, defina `EmitLegacyClaims` e `EmitStandardClaims` de forma explícita. Com leitores antigos, ligue os dois; mova os leitores para `sub`/`preferred_username` (ou para o `UserTokenDto`) e desligue o legado depois.
3. Com a configuração estrita ligada por padrão, rode a aplicação em homologação: uma chave desconhecida em qualquer seção do Tooark falha o startup e aponta o nome errado.
4. Suba para a v5.

## Modificado

- **Documentação**: READMEs do `Tooark.Notifications` e do `Tooark.Securities` (en/pt-BR) refletem o `Clear()` removido e os novos padrões das claims, com a nota de migração da 4.x.

## Infraestrutura do repositório

- **Validação da API pública**: a baseline do `EnablePackageValidation` fica desligada durante o desenvolvimento da major, porque as quebras acima são intencionais. Antes da publicação, a baseline volta para a última 4.x publicada e o `CompatibilitySuppressions.xml` registra só as quebras deste arquivo (`dotnet pack /p:GenerateCompatibilitySuppressionFile=true`).

---

## Impacto

- Quem já trocou `Clear()` por `ClearNotifications()` e definiu os dois sinalizadores de claims na 4.x não precisa mudar código ao atualizar.
- Quem depende do padrão das claims recebe tokens com `sub`/`preferred_username`: clientes que leem `id`/`login` direto do token param de encontrar as claims até ligar `EmitLegacyClaims` ou migrar a leitura.
- Compatível com .NET 8.0+ e .NET 10.0+.

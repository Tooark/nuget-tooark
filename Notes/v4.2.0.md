# Release Notes v4.2.0

Data de lançamento: 20/09/2026

## 🆕 Resumo

Versão com o **novo pacote `Tooark.Securities.OpenId`** (issue #46): padroniza como os projetos Tooark configuram autenticação OpenID Connect no ASP.NET Core, com presets de SSO para **Microsoft Entra ID** e **Google** e um caminho genérico para qualquer provedor OIDC. O pacote apenas configura os handlers nativos `OpenIdConnect`, `JwtBearer` e cookie — fluxo `code` com PKCE, validação de token e mapeamento de claims — sem SDK de provedor e sem implementar nenhum fluxo do protocolo. Acompanha a governança do repositório (política de segurança, guia de contribuição, código de conduta, templates de issue e PR, Dependabot e CI de pull request). Não há breaking changes.

---

## 🆕 Novo pacote: Tooark.Securities.OpenId

Entra e Google são provedores OpenID Connect e funcionam com o handler padrão `Microsoft.AspNetCore.Authentication.OpenIdConnect`, que já suporta PKCE. O que se repetia de projeto em projeto era a **configuração**: trocar o `ResponseType` padrão do handler (`id_token`, fluxo implícito) por `code`, desligar o mapeamento legado de claims, listar os emissores certos do Entra, aceitar as duas formas de emissor do Google, conferir o domínio do Workspace. O pacote fixa esse padrão uma vez.

Cada provedor é lido da subseção **`OpenId:{nome}`** e o nome vira o esquema de autenticação:

```json
{
  "OpenId": {
    "Entra": { "TenantId": "…", "ClientId": "…", "ClientSecret": "…" },
    "Google": {
      "ClientId": "…",
      "ClientSecret": "…",
      "HostedDomain": "tooark.com"
    }
  }
}
```

```csharp
builder.Services.AddTooarkEntraSso(builder.Configuration);    // login interativo: OpenIdConnect + cookie
builder.Services.AddTooarkEntraBearer(builder.Configuration); // API: JwtBearer
```

| Método                                | Handler       | Seção           | Esquema  |
| ------------------------------------- | ------------- | --------------- | -------- |
| `AddTooarkEntraSso` / `EntraBearer`   | OIDC / Bearer | `OpenId:Entra`  | `Entra`  |
| `AddTooarkGoogleSso` / `GoogleBearer` | OIDC / Bearer | `OpenId:Google` | `Google` |
| `AddTooarkOpenIdSso` / `OpenIdBearer` | OIDC / Bearer | `OpenId:{nome}` | `{nome}` |

Padrões aplicados aos handlers:

- **Fluxo `code` com PKCE** — o handler do ASP.NET Core nasce em `id_token`; o pacote fixa `authorization code` e liga o PKCE.
- **Claims com os nomes do OpenID Connect** — `MapInboundClaims = false`: `sub`, `email` e `name` chegam como estão.
- **Validação de emissor, destinatário e expiração** sempre ligada; `ValidIssuers` soma-se ao emissor do documento de descoberta.
- **HTTPS obrigatório** na descoberta, salvo `RequireHttpsMetadata = false` para desenvolvimento.
- **Falha no startup** — `ClientId`, `Authority`/tenant e segredo ausentes, endereços inválidos e tenant multi-tenant sem emissores são reportados no registro, com mensagens `Options.OpenId.*` traduzidas nos três idiomas.
- **Cookie compartilhado** — vários provedores de SSO na mesma aplicação usam um único cookie (`Cookies`), registrado uma vez; `SignInScheme` permite reutilizar um cookie da aplicação. O primeiro provedor registrado define os esquemas padrão, sem sobrescrever o que a aplicação já definiu.
- **O consumidor fala por último** — `ConfigureOpenIdConnect` e `ConfigureJwtBearer` rodam após os padrões e podem sobrescrever qualquer um.

Presets:

- **Entra** (`EntraOptions`): `Authority` derivada de `{Instance}{TenantId}/v2.0`; `preferred_username` como nome e `roles` (app roles) como papel; aceita os emissores **v2 e v1** do tenant (`sts.windows.net`, para APIs que ainda recebem tokens v1) e os destinatários `{ClientId}` e `api://{ClientId}`; tenant multi-tenant (`common`, `organizations`, `consumers`) **exige** `ValidIssuers`, porque o emissor publicado na descoberta é um marcador que nunca confere; `Instance` para nuvens soberanas.
- **Google** (`GoogleOptions`): `Authority` fixa; `email` como nome; aceita os emissores `https://accounts.google.com` e `accounts.google.com`; `HostedDomain` envia o `hd` na tela de login **e confere a claim `hd` do token** — a sugestão sozinha não restringe nada — rejeitando contas de outro domínio e contas pessoais, e a conferência sobrevive ao consumidor substituir `Events`.
- **Genérico** (`OpenIdOptions`): informe a `Authority`; clientes públicos (PKCE sem segredo) são aceitos. Presets próprios herdam de `OpenIdOptions` e sobrescrevem `Authority`, `ResolveValidIssuers`, `ResolveValidAudiences`, `Validate` e `ConfigureHandler` — é assim que Entra e Google são construídos — e se registram por `AddTooarkOpenIdSso<TOptions>`/`AddTooarkOpenIdBearer<TOptions>`.

Fora do escopo, por decisão da triagem da issue: authorization server, emissão de código e verificação PKCE própria (território de OpenIddict/Duende/Keycloak). Recursos que exigem o `Microsoft.Identity.Web` (Graph, cache de token distribuído, on-behalf-of) ficam para um eventual satélite `Tooark.Securities.Entra` — o critério para pacote próprio é "exige SDK do provedor", o mesmo de Storage (#21) e Secrets (#19).

O pacote declara o framework compartilhado `Microsoft.AspNetCore.App`, como o `Tooark.AspNetCore` e o `Tooark.Observability`: ele existe para configurar handlers do ASP.NET Core e não tem uso fora de uma aplicação ASP.NET Core. O agregador `Tooark` passa a incluí-lo.

## Adicionado

- `Tooark.Securities.OpenId` — novo pacote, descrito acima.
- `Tooark.Extensions` — traduções (en-US, pt-BR, es-ES) das mensagens `Options.OpenId.*` e `OpenId.HostedDomain.Invalid`.
- `Tooark` (agregador) — passa a referenciar o `Tooark.Securities.OpenId`.
- Governança do repositório: `SECURITY.md` (reporte privado por GitHub Security Advisories, prazos, escopo, safe harbor), `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), `SUPPORT.md`, `.github/CODEOWNERS`, `.github/FUNDING.yml`, template de pull request, issue forms (bug e feature) com links para o advisory privado, `dependabot.yml` (NuGet e GitHub Actions, semanal), workflow de CI para pull requests (build e testes nos dois TFMs), `.editorconfig` e READMEs bilíngues: na raiz e em cada pacote, `README.md` passa a ser em inglês (é o arquivo exibido no NuGet) e `README.pt-BR.md` traz a variante em português, com seletor de idioma no topo e links absolutos para o GitHub. O README raiz ganhou as seções de desenvolvimento local (build, testes e cobertura) e de suporte, e deixou de listar contribuidores.

## Impacto

- Adição compatível: nenhum pacote existente muda de comportamento.
- Quem usa o agregador `Tooark` passa a receber o `Tooark.Securities.OpenId` e os handlers `OpenIdConnect`/`JwtBearer` do ASP.NET Core como dependência transitiva. O agregador já exigia o framework compartilhado (`Tooark.AspNetCore`, `Tooark.Dtos`), então o requisito de runtime não muda.
- Compatível com .NET 8.0+ e .NET 10.0+.

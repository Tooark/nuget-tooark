# Release Notes v4.10.0

Data de lançamento: 18/11/2026

## 🆕 Resumo

Versão com as lacunas que apareceram ao adotar o Tooark em um projeto novo. Nenhum membro público muda de assinatura: a validação de pacote contra a v4.9.0 passa em todos os pacotes. Uma correção muda o comportamento de quem informa o identificador de uma entidade depois da construção; veja o [Impacto](#impacto).

- **Entidades com identificador informado.** As classes com auditoria ganham construtores que recebem o `id` junto com o criador. Até a v4.9.0 elas só geravam o identificador, e um `SetId` chamado depois era recusado em silêncio.
- **`SetId` lança em vez de acumular notificação.** Um identificador vazio, ou a troca de um identificador já definido, lança `BadRequestException`, como os demais `Set*` das entidades.
- **Nível do log das exceções tratadas configurável.** As `TooarkProblemDetailsOptions` definem o nível por faixa e por status. O padrão continua `Warning` para 4xx.
- **Falhas de validação do ASP.NET Core no formato do Tooark, opt-in.** Com `ConvertValidationProblems`, a validação dos controllers e das minimal APIs responde a mesma lista `errors` de `code`, `key` e `message` das exceções, e o cliente passa a receber um único formato.
- **Conversão explícita entre os dois formatos** com o `ValidationProblemExtension`, nos dois sentidos.

## ⚠️ Avisos para a v5

Nada abaixo muda nesta versão. Os avisos da [v4.8.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.8.0.md#️-avisos-para-a-v5) e da [v4.9.0](https://github.com/Tooark/nuget-tooark/blob/main/Notes/v4.9.0.md#️-avisos-para-a-v5) continuam valendo; estes são os que a v4.10.0 acrescenta.

- **4xx registrado em `Information` por padrão.** Na v5, `ClientErrorLogLevel` passa a valer `Information` quando não informado. Para continuar em `Warning`, informe `options.ClientErrorLogLevel = LogLevel.Warning`.
- **Conversão das falhas de validação ligada por padrão.** Na v5, `ConvertValidationProblems` passa a valer `true` quando não informada, e os clientes que leem o `errors` do `ValidationProblemDetails` como objeto por campo passam a receber a lista. Ligue a opção em homologação desde já para ajustar os clientes; para manter o formato do ASP.NET Core na v5, informe `false`.

## Adicionado

### `Tooark.Entities`

- **Construtores com identificador nas entidades com auditoria:** `InitialEntity(Guid id, CreatedBy createdById)` e o mesmo par em `DetailedEntity`, `VersionedEntity`, `SoftDeletableEntity` e `AuditableEntity`, além de `FileEntity(Guid id, FileStorage file, Title title, CreatedBy createdById)` e da sobrecarga completa do `FileEntity` com o `id` na frente. O identificador informado é o único atribuído, sem um `Guid` gerado antes, e a criação continua registrando o criador e a primeira atualização uma vez só. Um identificador vazio lança `T.ENT.BAS1`.
- Não há construtor só com o `id` nessas classes: o `CreatedBy` converte implicitamente de `Guid`, e um `: base(algumGuid)` existente passaria a significar o identificador em vez do criador, sem erro de compilação.

```csharp
public class Pedido : AuditableEntity
{
  private Pedido() { }

  public Pedido(CreatedBy createdById) : base(createdById) { }

  // Identificador informado por quem chama (chave de idempotência, importação, id gerado no cliente)
  public Pedido(Guid id, CreatedBy createdById) : base(id, createdById) { }
}
```

### `Tooark.AspNetCore`

- **`TooarkProblemDetailsOptions`**, configuradas com `services.Configure<TooarkProblemDetailsOptions>(...)`, só por código, e lidas do container da requisição a cada resposta:

  | Opção                       | Padrão    | O que faz                                                               |
  | --------------------------- | --------- | ----------------------------------------------------------------------- |
  | `ClientErrorLogLevel`       | `Warning` | Nível do log de uma exceção respondida com 4xx                          |
  | `ServerErrorLogLevel`       | `Error`   | Nível do log de uma exceção respondida com 5xx, com a pilha de chamadas |
  | `StatusCodeLogLevels`       | vazio     | Nível por status, que vence o da faixa; `LogLevel.None` tira do log     |
  | `ConvertValidationProblems` | `false`   | Responde as falhas de validação do ASP.NET Core na lista do Tooark      |

- **Conversão das falhas de validação.** Ligada, cada mensagem do objeto `errors` do `ValidationProblemDetails` vira um item da lista do Tooark, com o campo em `key`, o código padrão `T.ERR` e a mensagem traduzida. O `status`, o `type`, o `traceId` e as extensões do `CustomizeProblemDetails` continuam no corpo, e o `title` passa a ser a frase padrão do status, como nas exceções. O `CustomizeProblemDetails` roda antes da conversão, sobre o problema do ASP.NET Core: um `title` ou um `detail` definido nele é substituído.

  | Origem da falha                                                | Convertida                                                                      |
  | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
  | Validação automática do `[ApiController]`                      | Sim                                                                             |
  | Validação automática do `[ApiController]` com o envelope       | Não: o `AddTooarkModelStateEnvelope` continua respondendo o `ResponseDto`       |
  | `ValidationProblem()` de um controller                         | Sim                                                                             |
  | Validação das minimal APIs (`AddValidation`, .NET 10)          | Sim                                                                             |
  | `Results.ValidationProblem` e `TypedResults.ValidationProblem` | No .NET 10. No .NET 8 o framework escreve o corpo direto: use o `TooarkResults` |

- **`ValidationProblemExtension`** (`Tooark.AspNetCore.Extensions`): `ToNotificationItems` converte as mensagens por campo do ASP.NET Core (o dicionário ou o `HttpValidationProblemDetails`) em itens de notificação, e `ToValidationErrors` faz o caminho de volta, agrupando pela chave e traduzindo as mensagens. A conversão é explícita, e não um operador implícito, porque o caminho de volta perde o código de cada item.

```csharp
builder.Services.AddTooarkProblemDetails();
builder.Services.Configure<TooarkProblemDetailsOptions>(options =>
{
  options.ClientErrorLogLevel = LogLevel.Information;
  options.ConvertValidationProblems = true;
});
```

## Corrigido

### `Tooark.Entities`

- **`BaseEntity.SetId` lança `BadRequestException`** com `T.ENT.BAS1` (`Field.Empty;Id`) para um identificador vazio e `T.ENT.BAS2` (`Field.ChangeBlocked;Id`) para a troca do identificador de uma entidade que já tem outro. Até a v4.9.0 os dois casos só acrescentavam uma notificação: a entidade seguia com o identificador antigo e, sem conferir o `IsValid`, ninguém percebia. O `SetId` passa a seguir a regra dos demais `Set*` das entidades, que já lançavam sem deixar notificação.
- **O construtor `BaseEntity(Guid id)` lança** pelo mesmo motivo quando recebe `Guid.Empty`, em vez de criar a entidade inválida com o `Id` vazio.
- O que **não** muda: o construtor sem parâmetros continua gerando o `Id` com `Guid.NewGuid()`; informar de novo o mesmo identificador continua aceito, sem efeito; o Entity Framework atribui o `Id` lido do banco sem passar pelo `SetId`.

## Impacto

- Quem não chama o `SetId`, não constrói uma entidade com `Guid.Empty` e não configura as opções novas não precisa mudar nada: o log e as respostas de validação ficam como na v4.9.0.
- **`SetId` — confira antes de atualizar.** Procure chamadas a `SetId` nas entidades:
  - **No construtor de uma classe derivada** de `InitialEntity`, `DetailedEntity`, `VersionedEntity`, `SoftDeletableEntity` ou `AuditableEntity`, o construtor da base já gerou um `Guid`, então a chamada era recusada em silêncio e a entidade ficava com o identificador gerado. Na v4.10.0 o construtor lança `T.ENT.BAS2`. Passe o identificador ao construtor novo da base:

    ```csharp
    // v4.9.0: o SetId era recusado em silêncio e o pedido ficava com um Id gerado
    public Pedido(Guid id, CreatedBy createdById) : base(createdById)
    {
      SetId(id);
    }

    // v4.10.0
    public Pedido(Guid id, CreatedBy createdById) : base(id, createdById) { }
    ```

  - **Fora do construtor**, quem conferia o `IsValid` depois do `SetId` passa a tratar a `BadRequestException`.
  - **`new X(Guid.Empty)`** em uma entidade que herda direto do `BaseEntity` passa a lançar `T.ENT.BAS1`.
- **Log no .NET 8.** O `UseExceptionHandler` do .NET 8 registra toda exceção como `Error`, na categoria `Microsoft.AspNetCore.Diagnostics.ExceptionHandlerMiddleware`, antes de chamar o manipulador. O nível das `TooarkProblemDetailsOptions` só muda a entrada do Tooark; no .NET 10 o middleware não registra a exceção tratada, e a entrada do Tooark é a única.
- **Conversão no .NET 8.** O `Results.ValidationProblem` das minimal APIs não passa pelo serviço de Problem Details no .NET 8 e não é convertido: use o `TooarkResults.ValidationProblem`.
- Compatível com .NET 8.0+ e .NET 10.0+.
